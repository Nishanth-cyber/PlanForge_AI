# PlanForge — Planning Agent (Phase 3)

This document is the authoritative architectural specification and reference guide for the **Planning Agent** (Phase 3) of PlanForge.

---

## 1. Purpose & Responsibility Boundaries

The Planning Agent answers one question:
> **"HOW should validated user requirements be organized and represented for spatial allocation?"**

It transforms a complete, validated `Requirements` model into a strategic spatial program (`PlanningSpec`).

### Strict Architectural Boundaries

| Responsibility | Planning Agent | ASAA (Stage 3) | Geometry Engine (Stage 5) |
|---|---|---|---|
| Room Categorization & Functional Zones | **YES** | NO | NO |
| Room Allocation Priority & Rationale | **YES** | NO | NO |
| 4-Tier Relationship Graphs (Adjacency/Avoid) | **YES** | Consumes only | NO |
| Circulation & Entrance Intent | **YES** | Consumes only | NO |
| Multi-Floor Staircase Connectivity Intent | **YES** | Enforces footprint alignment | Constructs stair treads/risers |
| Spatial Partitioning / Bounding Regions | NO | **YES** | NO |
| Room Coordinates ($x, y$) & Polygons | NO | NO | **YES** |
| Walls, Doors, Windows Geometry | NO | NO | **YES** |

---

## 2. Input and Output Contracts

- **Input**: `Requirements` (from `app/models/requirements.py`), validated and complete.
  - If requirements are incomplete (e.g. missing plot dimensions or missing floor room lists), `PlanningAgent` raises `IncompleteRequirementsError`.
  - The Planning Agent **never** invents missing rooms or floors.
- **Output**: `PlanningSpec` (from `app/models/planning.py`).
  - Contains a list of `FloorPlanSpec` (one per floor), project-level `global_constraints`, and preserves `source_requirements_id`.

## 3. Core Architectural Principles

### 3.1. Stable Room Identity Preservation
Every `RoomSpec` generated by the Planning Agent carries:
- `id`: A unique identifier (e.g. `room_...`).
- `source_requirement_id`: The exact `id` of the upstream `RoomRequirement`.
This guarantees end-to-end traceability across the pipeline:
$$\text{Requirements} \longrightarrow \text{Planning} \longrightarrow \text{ASAA} \longrightarrow \text{LLM Design} \longrightarrow \text{Geometry} \longrightarrow \text{Validation}$$

### 3.2. Room Categorization & Functional Zones
Rooms are categorized by `RoomCategorizer` into architectural functional zones without distorting the user's original phrasing:
- **`social`**: `living`, `dining`, `drawing_room`, `lounge`, `reception`.
- **`private`**: `bedroom`, `master_bedroom`, `guest_bedroom`, `study`, `home_office`.
- **`service`**: `kitchen`, `bathroom`, `attached_bathroom`, `powder_room`, `storage`, `utility`, `laundry`.
- **`circulation`**: `foyer`, `hallway`, `corridor`, `staircase`.
- **`outdoor`**: `balcony`, `terrace`, `porch`, `veranda`, `garage`.
- **`other`**: `pooja`, `prayer`, `gym`.

`RoomSpec.original_name` retains the user's raw brief text for explainability.

### 3.3. Explainable Priority Calculation
`PriorityCalculator` assigns planning priorities (`"high"`, `"normal"`, `"low"`) accompanied by a structured `priority_rationale`:
- **`high`**: Primary functional anchors that anchor the layout (e.g. `living`, `master_bedroom`, `kitchen`).
- **`normal`**: Standard habitable, sanitary, and circulation spaces (e.g. `bedroom`, `dining`, `study`, `bathroom`, `foyer`, multi-floor `staircase`).
- **`low`**: Flexible service and peripheral outdoor spaces (e.g. `storage`, `utility`, `laundry`, `balcony`, `porch`).
- **Attached Dependency**: An attached room (e.g. ensuite) inherits dependency from its parent room and is assigned `"normal"` priority.

### 3.4. Four-Tier Relationship Graph
`RelationshipGraphBuilder` organizes spatial relations into four semantic tiers:
1. **REQUIRED ADJACENCY**: User-specified direct adjacency (e.g. `living ↔ dining`, `kitchen ↔ dining`).
2. **PREFERRED ADJACENCY**: Standard architectural adjacency best practices (e.g. `living ↔ foyer`, `dining ↔ kitchen`, `bedroom ↔ common bathroom`).
3. **SEPARATION (AVOID)**: Critical privacy or service separations (e.g. `garage ↔ bedrooms`, `attached_bathroom ↔ living/dining/kitchen`).
4. **ATTACHED**: Direct private suite coupling (e.g. `master_bedroom ↔ attached_bathroom` via `attached_to_room_id`).

#### Bidirectional Symmetry & Conflict Resolution
- The adjacency and avoid matrices are symmetric: $u \in \text{adj}[v] \iff v \in \text{adj}[u]$.
- Duplicate edges and self-loops ($u \in \text{adj}[u]$) are strictly prevented.
- **Conflict Resolution**: Avoid/Separation strictly overrides Preferred Adjacency.

### 3.5. Floor Assignment Preservation
Planning preserves the exact floor distribution defined in `Requirements.floors`. The planner never moves rooms across floors.

### 3.6. Circulation, Entrance, and Staircase Intents
- **Circulation Zones**: Identifies functional circulation demands (`public_circulation`, `private_circulation`, `service_circulation`, `vertical_circulation`) with descriptive planning notes. No corridor geometry is created.
- **Entrance Intent**: Floor 1 carries `entrance_intent` capturing facing direction, preferred access room (e.g. `living`, `foyer`), and entry role. No door geometry is created.
- **Staircase Intent**: Multi-floor plans carry `staircase_intent` capturing connecting floors (e.g. `[1, 2]`) and `alignment_required=True`. No stair treads, risers, or polygons are created.

### 3.7. Global Planning Constraints
Formulates project-level constraints stored in `PlanningSpec.global_constraints`:
- Boundary constraints: `plot_dimensions`, `plot_area_sqm`, `setbacks`, `orientation`.
- Multi-floor constraints: `staircase_aligned=True`, `target_floors`.
- Topological constraints: `privacy_buffering=True`, `circulation_continuity=True`.

## 4. Determinism & Non-Invention Guarantees

1. **Deterministic Execution**: Purely deterministic rule-based algorithms with zero LLM calls. Given the same `Requirements`, `PlanningAgent` produces identical `PlanningSpec` programs.
2. **Zero Synthetic Rooms**: If an input brief lacks rooms for Floor 2, the Planning Agent raises `IncompleteRequirementsError`. It never synthesizes placeholder rooms.
3. **Zero Physical Geometry**: No Cartesian coordinates ($x, y$), no Shapely polygons, no bounding boxes, no wall lines, and no door swings are produced in Phase 3.
